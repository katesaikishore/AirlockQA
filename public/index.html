Browser tests with a safety door.

AirlockQA clicks through your website like a real customer to check that everything works. Each test runs behind a safety door that checks requests against your rules, so risky ones like refunds, deletes or real passwords can be blocked before they reach your site. It covers traffic that goes through the Airlock gateway and proxy, and every run ends with signed run evidence that shows the recorded log was not changed after signing.

Record a browser session, compile it to Playwright TypeScript, and run it locally or from CI. Requests through the Airlock gateway and proxy are checked against host, path and method rules, and every run emits a hash-linked, signed evidence bundle.

From a few clicks to a signed result.

Request policy · Phantom credentials

A safety door for every request.

Your test talks to payment providers, email services and your own APIs. AirlockQA checks each request on the way out: safe ones go through; risky ones — refunds, deletes, unknown websites — are stopped. In local runs the test only carries a stand-in key; the real one is added at the door, and only for places you approve.

  • Refunds, deletes and unknown sites are blocked by default
  • Stand-in keys instead of real passwords in local test browsers
  • A clear log of every allow and every block

The gateway and proxy intercept requests and evaluate host, path and method rules under a default-deny action. Phantom tokens are swapped for configured real values only on allowedHosts, and matching upstream responses are sanitized before they reach the page.

  • defaultAction: "BLOCK" with allow and deny host lists
  • Per-secret allowed hosts, methods and blocked paths
  • Verdicts logged as ALLOWED, BLOCKED or SANITIZED

Request policy covers requests through the Airlock gateway and proxy only. It isn’t an OS-level firewall, and hosted runs hold none of your application secrets.

Self-healing locators

When your design changes, tests find their way.

Renamed a button or moved it? That’s where most tests break. AirlockQA looks for the same element by its label, text and place on the page, fixes the step, and shows you exactly what it changed so a person can approve it.

When a selector misses, the healer scores candidates by test id, accessible name, text and structure. Above the confidence threshold (0.8 by default) it resolves the locator and writes the before/after DOM to a mutation dataset you can inspect with airlock dataset.

Every repair is a suggestion you can accept or reject in the console.

Browser checkpoints · Forks

Save points: log in once, test many paths.

Like a save point in a game. AirlockQA remembers a moment — signed in, cart filled — and starts new tests from there, side by side, instead of repeating the same steps every time.

A checkpoint captures storage state, session storage, URL and a DOM hash, then restores them into fresh Playwright contexts. airlock fork cart_ready --workers 5 runs variations in parallel from the same warm state.

Browser state only — not VM or process memory.

Execution evidence

Signed run evidence, for every run.

Each run writes down what happened, step by step, and signs it. If anyone changes a line later, verification fails. Share it with a teammate or a client as a record of what was tested.

Every event becomes a hash-linked ledger block; the run’s Merkle root is signed with HMAC-SHA256 or Ed25519. airlock audit recomputes the chain and flags tampering.

It shows the recorded log was not changed after signing. It does not show that your application is secure.
